# 設計判断と未決事項

## Accepted — 現時点で確定として実装する

| ID | 判断 | 理由 |
|---|---|---|
| ADR-001 | P0は単一デモユーザー・認証なし、Google認証はP1 | 自己分析とESのE2E完成を優先する |
| ADR-002 | 自己分析は独自4軸（Focus↔Connect、Plan↔Experiment、Mastery↔Impact、Stable↔Dynamic） | タイプ診断を避け、経験へ遡れる傾向と状況差を表す |
| ADR-003 | ユーザー確認済み経験だけをES事実根拠に使う | AIによる役割・数字・成果の創作を防ぐ |
| ADR-004 | 企業情報は出典ID・URL・取得日時・引用を持つ | 企業の非公開特徴を断定しないため |
| ADR-005 | 検査と推敲を別処理にし、推敲後も再検査する | 同一生成内の自己評価だけに依存しないため |
| ADR-006 | HTTP APIは`/api/v1`、同期JSON | 9日間のMVPでフロント・バック統合を簡単にする |
| ADR-007 | DBはSQLite | 同一PC・単一ユーザーでサーバー構築を不要にする |
| ADR-008 | 企業情報の文章貼り付けをP0、URL取得をP1 | 外部ページ仕様にP0完成を依存させない |
| ADR-009 | ユーザー原文を基に、全履歴から関連根拠を選んだ提出可能品質の完成版ES案を生成する | 本人性と根拠を維持しながら、そのまま提出できる完成度を目指す |
| ADR-010 | 数値confidenceをユーザーに表示しない | 擬似的な精密さを避ける |
| ADR-011 | ORMはPrisma | AI・バックエンド担当がPrismaに習熟しており、型・migrationを共有しやすい |
| ADR-012 | LM Studio接続は`@lmstudio/sdk`をAdapter内で使用 | Zod構造化出力とモデル情報取得をTypeScriptで統一する |
| ADR-016 | ES文字数はUnicodeコードポイントで数える | 日本語と文中の英字・コード識別子を一貫して数える |
| ADR-017 | 推奨モデルはQwen3.5 9BのGGUF Q4_K_M | 16GB VRAM内に収まり、日本語・構造化出力の評価を始めやすい |
| ADR-018 | ESの言語は日本語を基本とし、英字・コード・製品名を許可する | 文中の英語をエラーや翻訳対象にしない |
| ADR-019 | 企業提案前に登録済み公式URLを取得し、根拠付き企業事実を更新する | LLMの記憶だけで企業を提案しない |
| ADR-020 | ハッカソン版の企業候補はチーム登録の10〜20社に限定する | 1週間でデータ品質・取得成功率・デモ再現性を確保する |
| ADR-021 | 実装順は自己分析、ES推敲、企業提案 | プロダクトの前提となる自己分析の完成度を最優先する |
| ADR-022 | 4軸は強制二択にせず、両方・状況依存・根拠不足を正式に扱う | 片側の証拠不足から反対側を推測する誤判定を防ぐ |
| ADR-023 | 「終わりたい」の検出だけでセッションを完了しない | 誤検出による会話終了を防ぎ、本人確認後だけfinalizeする |
| ADR-024 | 「初めから」は進行中セッションを`ABANDONED`にして新規作成する | 過去結果と確認済み経験を失わず、再開対象を一意にする |
| ADR-025 | セッション結果は内部保存するが、ホームに過去セッション一覧は表示しない | ホームでは全履歴からの現在の総合傾向へ集中させる |
| ADR-026 | ESは数値採点せず、完成版ES案の下に根拠状態・問題箇所・改善理由を表示する | 根拠不明な精密スコアを避け、修正理由を確認可能にする |
| ADR-027 | ESの企業情報はP0では任意 | 画像のES入力フローを企業登録なしでも完走できるようにする |
| ADR-028 | 新セッション固有結果には過去経験を混ぜず、ホーム総合傾向とESでは全履歴を使う | セッションごとの変化と、蓄積した自己理解の両方を保持する |
| ADR-029 | 完了したAIチャット1件につきセッション自己分析レポートを1件保存する | 会話単位の結果を総合プロフィールとESの入力にできるようにする |
| ADR-030 | USER回答が1件以上あれば結果生成を許可し、確認済み経験数を完了条件にしない | データ量は生成可否ではなく注意表示で扱う |
| ADR-031 | ホーム総合傾向は全正式根拠から再計算し、セッション位置の数値平均をしない | 状況依存や根拠量を壊さず、擬似的な数値精度を避ける |
| ADR-032 | `completedSessionCount < 2`または`confirmedExperienceCount < 3`ならデータ不足を表示する | 結果は表示しつつ、情報量が少ないことを明示する |
| ADR-033 | ESには全確認済み経験・全セッションレポートを候補として渡し、設問に合う根拠をAIが選ぶ | 文字数内へ全経験を無理に列挙せず、蓄積を漏れなく候補化する |

## Open Questions

現時点で、P0実装を止める未決事項はない。データ不足表示の初期閾値はADR-032とし、実機評価で表示頻度を確認して調整する。

## Deferred Decision — ハッカソン後に決める

### 任意企業をWeb全体から発見する方式

ローカルLLM自身には最新Web検索能力がない。公式URLを取得するには、取得前にURLを知っている必要がある。

ハッカソン版は、チームが10〜20社の企業名・公式採用URLを候補カタログへ登録し、
その範囲で公式情報を再取得・比較・提案する。

任意企業をWeb全体から探す場合は、Google Custom Search、Brave Search等の検索APIか、
検索結果を提供する別サービスが必要になる。検索サービスの利用規約、費用、APIキー、
公式サイト判定、検索失敗時の処理を比較してから採用方式を決める。

## Resolved Inputs — 2026-08-02

- デモPC: Ryzen 9 9900X、DDR5 64GB、Radeon RX 7800 XT、VRAM 16GB想定
- LM Studio: 初心者向け手順を`docs/lm-studio-setup.md`へ定義
- ORM: Prisma
- 企業情報: 文章貼り付けが基本。企業提案時は登録済み公式URLを自動取得
- 企業候補: チーム登録の10〜20社。任意Web検索はハッカソン後
- 優先順位: 自己分析を最優先、次にES推敲、余裕があれば企業提案
- ES: 日本語を基本とし、文中の英語、製品名、技術用語、コード識別子を許可

## Resolved Inputs — 2026-08-04

- 自己分析の基本軸を、Focus↔Connect、Plan↔Experiment、Mastery↔Impact、Stable↔Dynamicの独自4軸へ変更
- ホームから初回開始・続きから・初めからへ分岐し、進行中チャットを再開できるユーザーフローを採用
- 終了意図はチャットから検出してよいが、本人の明示確認後だけ分析結果を確定
- ホームに4軸のグラフ／コメントと自己分析結果を表示
- ES入力、検査コメント、訂正版、再検査までを一連のフローとして定義
- 当時はP0認証、分析履歴表示、ES採点方式を承認待ちの既定値として要件化（2026-08-05に解決）

## Resolved Inputs — 2026-08-05

- GoogleログインはP1で確定
- 完了したAIチャット1セッションにつき自己分析結果を1件保存
- 確認済み経験3件以上という完了条件と、複数経験を必須とする条件を撤廃
- ホームには過去セッション一覧を表示せず、全セッションから再計算した総合4軸傾向、強み、弱み・注意点を表示
- データ量が少なくても結果を表示し、注意文と件数を併記
- ESでは全履歴を候補としてAIへ渡し、設問と文字数に合う経験を選んで完成版ES案を生成
- 完成版ES案の下に根拠状態・問題箇所・改善理由を表示し、数値点数は使用しない
